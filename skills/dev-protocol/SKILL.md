# dev-protocol — 인터뷰 → 레퍼런스 → 구현노트 → 퀴즈

## Overview
구현·디자인·비가역 작업의 전 과정을 감싸는 개발 프로토콜. 목적 세 가지:
1. **착수 전** — 사용자가 다 지시하지 못한 부분까지 예측·확정해서 재작업(회복 비용)을 없앤다.
2. **작업 중** — 판단 근거와 이탈을 프로젝트별 "지도"에 남겨, 다음에 비슷한 사건·복병·unknown을 만났을 때 참조한다.
3. **작업 후** — 사용자가 이번 변경을 제대로 이해했는지 퀴즈로 확인한다.

**발동 기준**: 코드 생성·수정·설계·디자인 등 "만드는" 작업, 비가역 작업. 단순 조회·질문·재도자 가능한 것은 프로토콜 없이 그냥 진행.

## 절대 게이트

다음 규칙은 편의상 생략할 수 없다.

1. **실제 사용자의 답만 승인이다.** 현재 대화에서 사용자가 직접 답한 내용만 gate evidence로 인정한다. 모델의 추론, subagent·reviewer의 선택, 이전 초안, 저장소에 적힌 가정은 사용자 승인을 대신하지 못한다.
2. **착수 허가와 결정 승인을 구분한다.** `ㄱㄱ`, `진행해`, `알아서`, `테스트니까 해봐` 같은 짧은 응답은 직전에 설명한 다음 단계의 착수만 허가한다. 아직 제시하지 않은 요구사항, 디자인 방향, 시안, 범위 이탈까지 승인한 것으로 확대하지 않는다.
3. **위임은 선택지를 본 뒤에만 유효하다.** 사용자가 선택을 위임하려면 선택지와 영향이 먼저 제시돼야 한다. 그 이전의 포괄적 위임은 미정 사항을 임의 확정할 근거가 아니다.
4. **필수 질문이 남으면 STOP한다.** structured question tool이 있으면 사용하고, 없으면 채팅으로 한 질문을 묻고 응답을 기다린다. 질문을 보낸 같은 turn에서 구현을 계속하지 않는다.
5. **쓰기 전에 gate evidence를 남긴다.** 구현노트에 실제 질문·사용자 답·확정 범위를 기록한다. 필요한 gate가 비어 있으면 application code, schema, migration, 디자인 source를 수정하지 않는다. 규칙·프로젝트 탐색 같은 read-only 확인은 허용한다.

디자인 작업은 이 공통 gate에 더해 해당 디자인 스킬의 방향 선택·시안 승인 gate를 모두 통과해야 한다.

## 프로젝트 워크플로 skill 이 있으면 그것을 따른다

저장소에 브랜치·PR·배포 절차를 고정한 skill 이 있으면 **임의 절차를 만들지 말고 그것을 호출한다.**
이 문서는 *무엇을 확인하고 무엇을 남기는가*(인터뷰·구현노트·이탈 리뷰)를 소유하고,
*어떻게 브랜치를 따고 어디에 머지하고 어떻게 배포하는가*는 프로젝트 skill 이 소유한다.

찾는 법: 저장소의 `.claude/skills/` 와 `AGENTS.md` 의 skill 라우팅 표.

프로젝트 skill 이 이 문서의 절대 게이트를 약화시키지 않는다. **둘 다 통과해야 한다.**
특히 운영 배포는 절대 게이트 2번(착수 허가 ≠ 결정 승인)이 그대로 적용된다 —
앞선 `ㄱㄱ` 를 머지 승인으로 확대하지 않는다.

## ① 인터뷰 (착수 전, 애매하면 무조건)
- 요청이 조금이라도 애매하거나 확정적이지 않다고 판단되면 **착수 전에** 인터뷰한다. "대충 이 뜻이겠지"로 진행 금지.
- **AskUserQuestion으로 한 번에 하나씩(최대 한 화면 2문항)**, 답변에 따라 다음 질문을 바꾼다. 취조하듯 — 사용자가 지시하지 않은 결정 지점(엣지케이스, 우선순위, 범위 경계, 데이터 처리, 실패 시 동작)을 AI가 먼저 예측해서 질문으로 만든다.
- 각 질문에는 **추천 옵션을 첫 번째로** 두고 근거를 description에 쓴다.
- 인터뷰 종료 조건: "이대로 만들면 재작업 없다"고 확신할 때. 종료 시 확정 사항을 표로 요약하고 시작한다.
- 새 제품·새 디자인처럼 정본이 없는 작업은 최소 한 번의 실제 사용자 답변 또는 명시적 요약 승인을 받은 뒤에만 정본 문서와 구현을 쓴다. 저장소에서 합리적으로 추론할 수 있어도 확인 round를 없애지 않는다.

## ② 레퍼런스 요구 (인터뷰로도 부족하면)
- 말로 확정이 안 되는 것 — **특히 디자인/UI/UX** — 은 레퍼런스를 요구한다: 스크린샷, URL, 유사 서비스, 손그림, 기존 화면 중 "이 느낌" 지목.
- 레퍼런스를 받으면 "무엇을 채택하고 무엇은 다르게 갈지"를 한 줄로 확인받고 시작한다.

## ③ 구현노트 (작업 중 — 프로젝트의 지도)
**위치**: `<project>/docs/impl-notes/YYYY-MM-DD-<slug>.md` (작업 단위로 1파일, 누적. HANDOFF.md와 역할 분리 — HANDOFF는 "지금 상태 인계" 덮어쓰기, 구현노트는 "사건 이력서" 누적)

- **시작 전**: `docs/impl-notes/`의 기존 노트를 훑어 비슷한 사건·복병 이력이 있는지 확인하고, 있으면 반영한다 (지도 활용).
- **첫 write 전**: `## Gate evidence`에 질문, 사용자 답, 확정 범위, 아직 미정인 항목을 기록한다. 답변 없이 추론한 내용은 `미승인 가정`으로 표시하며 구현 근거로 쓰지 않는다.
- **작업 중**: 계획과 달라지는 순간마다 기록. **계획과 달라지면 보수적인 쪽을 택한다** (기존 동작 보존 > 새 시도, 좁은 변경 > 넓은 변경).
- **이탈 항목은 반드시 `⚠️ DEVIATION` 마킹** — 리뷰 대상임을 표시.

템플릿:
```markdown
# YYYY-MM-DD <작업명>

## 목표 / 확정 사항
- (인터뷰 결과 요약)

## Gate evidence
- 질문: (사용자에게 실제로 제시한 질문)
- 사용자 답: (현재 대화의 실제 답)
- 승인된 범위: (이번 write가 허용된 범위)
- 미승인 가정: 없음 / (구현하지 않고 남겨둔 항목)

## 계획
- (단계 요약)

## 판단 근거
- (선택지가 있었던 지점과 고른 이유)

## ⚠️ DEVIATION (계획과 달라진 것 · 복병)
- ⚠️ <무엇이, 왜 달라졌나> → 택한 보수적 대안: <무엇> → 리뷰: [ ] 미완 / [x] YYYY-MM-DD 사용자와 리뷰
- (없으면 "없음")

## 다음에 참고 (unknown 대응 이력)
- (이 프로젝트에서 재발 가능한 함정·패턴)
```

## ④ 이탈 리뷰 + 퀴즈 (구현 작업 완료 시마다)
작업 종료 직후, 이 순서로:
1. **이탈 리뷰**: 구현노트의 `⚠️ DEVIATION` 항목을 사용자와 함께 리뷰 — 각 항목에 대해 "그대로 승인 / 개선(재작업) / 계획 자체 수정" 결정을 받고 노트에 리뷰 완료 표시.
2. **퀴즈**: AskUserQuestion으로 **객관식 2~3문항** 출제 (AI가 출제, 사용자가 답). 출제 범위: 핵심 변경점, 영향 범위, 이탈 사항. 그럴듯한 오답을 섞는다.
3. **오답이면** 그 부분만 다시 설명하고 넘어간다 (재시험 없음). 전부 정답이면 한 줄 축하로 종료.

> 퀴즈는 구현 작업 완료 시에만. 조회·설명 턴에는 하지 않는다.

## Gate 위반 복구

필수 gate를 건너뛴 사실을 발견하면 즉시 다음 순서로 복구한다.

1. 추가 write를 멈춘다.
2. 승인 없이 만든 결과를 `미승인 초안`으로 표시하고 commit·push·배포하지 않는다.
3. 누락된 질문 또는 선택지를 사용자에게 제시하고 응답을 기다린다.
4. 사용자가 승인한 범위만 보존하고 나머지는 재작업 대상으로 기록한다.
