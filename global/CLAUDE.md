# 공통 작업 규칙 (Claude × Codex)

> 이 파일이 개인 글로벌 규칙의 정본이다. Claude는 `~/.claude/CLAUDE.md`에서 `@import`로 읽고,
> Codex는 `~/.codex/AGENTS.md` 심링크로 같은 파일을 읽는다. 규칙을 바꾸려면 이 파일만 고친다.
> 에이전트 홈(`~/.claude`, `~/.codex`)의 복사본을 직접 고치지 않는다 — 다음 bootstrap에서 덮인다.

## 크로스 에이전트 원칙

- **규칙 소스는 하나:** 개인 글로벌 규칙은 이 파일에만 둔다. 도구 중립적인 표현으로 쓴다.
- **워크플로 소스도 하나:** 재사용 워크플로는 `skills/<name>/SKILL.md`(Agent Skills 공개 표준)에 둔다.
  같은 파일이 Claude(`~/.claude/skills`)와 Codex(`~/.agents/skills`) 양쪽에서 그대로 동작한다.
- **스킬 작성 위치:** 새 스킬을 에이전트 홈에 직접 만들지 않는다. 이 레포의 `skills/<name>/`에 만들고
  `./bootstrap.sh`를 돌려 양쪽에 링크한다.
- **플랫폼 번역:** 사용자 입력·명령·라이프사이클은 각 에이전트의 네이티브 방식을 쓴다
  (예: Claude의 `AskUserQuestion` ↔ Codex의 일반 프롬프트). 스킬이 특정 플랫폼 도구명을 쓰면
  자기 플랫폼의 등가물로 해석한다 — 그 단계를 건너뛰지 않는다.
- **로컬 전용 설정은 로컬에:** 권한, 크리덴셜, GUI/TCC 절차, 계정 정보는 공유 정책이 아니다.
  양쪽 에이전트에 공통으로 적용되는 "의도"만 이 파일에 적는다.

## 작업 규칙

### 언어
- 사용자와는 한국어로 대화한다. 코드·명령어·기술 용어는 영어 그대로 둔다.

### 터미널은 에이전트가 직접 친다
- 셸 명령은 **에이전트가 직접 실행**한다. "터미널 열고 이거 직접 실행하세요"로 떠넘기지 않는다.
- 에이전트가 물리적으로 할 수 없는 경우(암호 입력, GUI 권한 승인, OS 권한 다이얼로그)에만
  정확한 명령어·클릭 경로를 주고 **왜 넘기는지 이유를 밝힌다.**

### Plan / Execute 분리
- 사소하지 않은 요청은 **(1) Plan**(목표·영향 파일·단계·검증 방법) → **(2) Execute**(실행) 순서로 간다.
- 한 단계짜리 사소한 작업은 plan을 생략해도 된다. 여러 단계·여러 파일·되돌리기 어려운 작업은 생략 불가.

### 완료 기준
- 코드 작업 후에는 프로젝트의 `build`와 `lint`(가능하면 `test`)가 **실제로 통과하는 걸 측정한 뒤에만**
  완료를 선언한다. 증거 없는 "done"은 금지.

### 커밋 / 푸시
- 커밋·푸시 전에는 항상 사용자에게 확인받는다. 기본 브랜치에 있으면 브랜치를 먼저 판다.
  (예외: 개인 동기화용 레포는 main 직접 푸시가 정상 워크플로)

### 마이그레이션 안전 (Supabase 등)
- DB 마이그레이션은 되돌릴 수 없다. **`--dry-run`으로 diff 확인 → 사용자 승인 → 실제 적용** 순서만 허용한다.

### Docker는 띄운 세션이 끝낼 때 반드시 내린다
- Docker Desktop VM은 컨테이너를 모두 껐어도 램 수 GB를 계속 물고 있다. "컨테이너만 stop"으로는 부족하다.
- 작업 중 컨테이너를 띄웠으면(`docker run` / `docker start` / `docker compose up` 등) **그 작업 단위가 끝나는 시점에 같은 세션에서 되돌린다**: `docker compose down`. volume은 삭제하지 않는다.
- 세션 종료 시 그 세션이 띄운 컨테이너가 남아 있으면 안 된다. 정리 후 **실행 중 컨테이너가 하나도 없으면 Docker Desktop 자체도 종료**한다 — `docker desktop stop --detach --force`, 폴백 `osascript -e 'quit app "Docker"'`.
- **남의 것은 끄지 않는다.** 다른 세션·사람이 쓰고 있는 컨테이너는 유지한다.
- 새로 띄우기 전에 이미 떠 있는 것을 먼저 본다(`docker ps -a`). `Restarting` 루프에 빠진 컨테이너는 램·CPU만 태우므로 즉시 `docker rm -f`로 제거한다.
- `dev-resource-guard` 훅이 이 절차를 세션 종료 시 자동 수행한다(정리는 detach된 프로세스라 세션 종료를 지연시키지 않는다). 일시적으로 막으려면 `AGENT_DOCKER_GUARD_KEEP=1`.

### HTML 결과물은 로컬 서버 URL로 열어준다
- HTML 결과물(슬라이드, 리포트, 대시보드 등)을 보여줄 때 `open`에만 의존하지 않는다 —
  `open`은 세션이 도는 머신 화면에만 뜨고, 사용자는 다른 기기에 있을 수 있다.
- 해당 디렉토리를 **로컬 HTTP 서버로 서빙**하고(`python3 -m http.server <포트> --bind 0.0.0.0`, 백그라운드)
  LAN IP URL을 준다. 한글 파일명은 URL 인코딩하고, 200 응답을 확인한 뒤 URL을 전달한다.
- **HTML에만 적용.** md·텍스트는 경로를 알려주거나 내용을 대화로 보여준다.
- 리뷰가 끝나면 서버를 내린다. 배포 파이프라인이 있으면 push 이후에는 배포 URL을 정식 경로로 안내한다.

### 작업 인계 (HANDOFF)
- 작업이 의미 있게 진전되거나 세션이 끝날 때, `docs/handoff/HANDOFF.md`가 있으면 갱신한다:
  **## Next actions / ## Decisions & context / ## Open items & blockers**.
- 매 턴이 아니라 의미 있는 단위마다 한다.

### 개발 프로토콜 — `dev-protocol` 스킬
- **구현/되돌리기 어려운 작업**(코드 작성·수정, 아키텍처, 설계)에 적용한다. 단순 조회·질문은 면제.
- ① 요청이 조금이라도 애매하면 **착수 전에 인터뷰**한다. 한 번에 하나씩, 사용자가 지정하지 않은
  결정 지점을 먼저 예측해서 질문으로 만든다.
- ② 그래도 불명확하면(특히 디자인) **레퍼런스를 요청**한다.
- ③ `<project>/docs/impl-notes/`에 작업당 한 파일씩 **구현 노트**를 쌓는다. 시작 전에 기존 노트를
  지도로 삼아 읽는다. 계획에서 벗어날 때는 **보수적인 선택지**를 고르고 `⚠️ DEVIATION`으로 표시한다.
- ④ 구현이 끝나면 **이탈 리뷰 → 2~3문항 객관식 이해도 퀴즈**로 마무리한다.
- 사용자의 짧은 착수 허가("ㄱㄱ", "해줘")를 **미정 사항에 대한 승인으로 확대 해석하지 않는다.**

### 브랜치 개발 환경 — `feature-flow` 스킬
- 표준 모델: `develop → feat/<x> → develop 머지 → main 머지(배포)`. main/develop 직접 편집 금지.
- `git checkout develop && git pull` → `git checkout -b feat/<x>` → 작업 → `gh pr create --base develop`.
- Supabase Branching + Vercel 연동 레포는 **PR을 열면 격리된 DB 브랜치 + preview URL + env가 자동 생성**된다
  → preview에서 개발·테스트한다.
- feat→develop 머지는 통합, **develop→main 머지가 운영 배포이며 운영 DB에 마이그레이션이 적용된다.**
